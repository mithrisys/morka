# Edit a Morka project

Start with the project manifest used by the current draft. Apps use `morka.project.json`. Read `project_files` for editable file contents, `project_paths` for the file inventory, and `project_instructions` for the project's active rules and skills, including imported Shadows. Follow the existing layout. Use native `apply_patch` in the project draft. Morka validates the draft, then publishes its changes. If paths move, update their references in the manifest.

For a standard Morka Git repository, the draft root corresponds to `app/`. Edit paths relative to the draft root. The outer repository owns `README.md`, `AGENTS.md`, `package.json`, `package-lock.json`, Git metadata, and `.morka/`. Keep those outer files intact. The app has its own editable package.json and package-lock.json inside this draft (app/ in the repository); declare arbitrary app dependencies there. Keep assets and services inside the draft.

Use the app's Shadows panel to install or remove a Shadow. Direct package authoring to New Shadow or Open Shadow so it uses the independent package repository.

## Startup layout

Morka apps run as independent managed Node services. Keep their `package.json`, `package-lock.json`, source and assets inside this draft. Set `runtime` to `{"type":"node","script":"start"}` in the version 1 manifest. The default readiness endpoint is `/health`. Define `scripts.start` as a foreground production server, for example `node server.mjs`, and bind to `Number(process.env.PORT)` and `process.env.HOST` (loopback). Never hardcode the managed internal port. `process.env.MORKA_APP_ORIGIN` is the stable browser origin; use it for absolute redirects and trust proxy headers only from the loopback proxy. Frontend code calls its backend over same-origin HTTP. Retain the starter script /__morka/bridge.js in HTML when using window.morka host agent actions; register actions with the top-level agentActions definitions/skills paths. Do not expose agent definitions, private configuration or data directories through static file serving.

Declare packages in this app's package.json, including build tools in devDependencies. Add `scripts.build` when a bundler/transpiler is needed (Vite, React, TypeScript, etc.). `scripts.start` and its server dependencies must work after devDependencies are pruned. Keep the existing lockfile so npm can update it in place. After draft edits, Morka resolves the lockfile, runs `npm ci` with dev dependencies in an isolated staging directory, executes build and optional `scripts["morka:check"]`, prunes dev dependencies, and seals an immutable release. For a request to install a package or run the app build, use this host workflow. In your reply, describe the edits and say that Morka will report npm and build results in the turn activity. Only report a verification result when you have real command output. The packaged app contains the matching standalone Node/npm pair, headers, production node_modules and build output. npm modules and native addons use this bundled Node ABI, never Electron's ABI. Do not rely on node_modules installed in the chat draft; it is never published. Local `file:` dependencies must be vendored under this draft, never point outside app/. Public registries, private registries and Git dependencies are supported through npm; registry credentials belong in the app's private runtime profile (`runtime/<app-id>/npm/npmrc`), not source. Private `npm.env` and `build.env` in that profile supply explicitly configured variables for installation and build/check scripts respectively; host API keys and the host npm configuration are not inherited.

Keep production servers healthy without writes or jobs during warmup. Morka starts a candidate while the current release still serves requests, then drains writes and switches the stable proxy only after health succeeds. The server's `globalThis.morkaRuntime.isActive()` indicates whether it owns the active release. Start background work on `process.on("morka:activate", ...)`, stop it on `process.on("morka:retire", ...)`, and check `isActive()` before committing scheduled work; use persistent idempotency/fencing for jobs. Do not run destructive schema migrations or send external messages during startup/health checks. Explicit live schema migrations use `runtime.migration: {"id":"add-field-v1","script":"migrate","compatibility":"backward-compatible"}`. Migration scripts must be transactional/idempotent, and compatible with both old and new code. Each migration ID runs once for the app. Code rollback never restores an old copy of user data. Breaking schema changes require a separate data migration design, not an ordinary visual edit.

Pure linked CSS edits without a build step are overlaid at the stable proxy without restarting the server or recreating the page. Other edits produce a new release and preserve the UI through the lifecycle hooks below. Install/build failures keep the published source and running app intact and are returned for one automatic repair attempt; unresolved drafts are preserved. Runtime health failures keep the previous running release active. Morka owns dependency installation and activation; never ask the user to run npm, press Run or reopen the app after an app edit.

## Preserve user state during live edits

Morka replaces linked CSS without recreating the page. For code or markup updates it preserves the current route, history state, form values, focus, selections and scrolling. Keep element IDs, input names and state keys stable across edits. Do not reset user data, navigation or existing state to show a visual change.

Every app with in-memory UI state (filters, selected tabs/items, open panels, wizard steps, editor drafts) must expose `window.morkaLifecycle = { ready, beforeUpdate, capture, restore }`. `ready` is the promise for initial data loading; optional `beforeUpdate()` flushes pending work. `capture()` returns JSON-serializable UI state and `restore(state)` restores it after `ready`, tolerating missing fields from older versions. Merge new fields into existing hooks. Persist business data independently; never use this transient UI snapshot as the database. Do not include passwords, tokens or database contents in custom snapshots. Morka waits for tracked requests before restarting a service and defers an update if a selected file or unfinished operation cannot safely survive it.

For example, retain a task filter with `capture: () => ({ filter })` and `restore: state => setFilter(state?.filter ?? "all")`, with `ready: loadTasks()` so restoration happens after the initial render. Form values are restored by Morka; retain additional application state explicitly.

Store app databases and user files under `process.env.MORKA_DATA_DIR`, which Morka keeps outside source drafts. Existing user data paths must remain usable or be migrated without overwriting data. `.morka-data/`, SQLite/database files and their journal/WAL sidecars are excluded from source snapshots and cannot be published by source edits. Keep explicit user-requested data migrations separate from presentation edits.

## Agent actions

Use `morka-agent-action` to add a control that sends data to an agent. Put app-specific integrations in the app backend.
